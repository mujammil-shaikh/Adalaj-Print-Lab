# 04 — Batches, Allocations & Material Accounting

**Primary source:** `src/components/batches/BatchesView.tsx`; persistence/mutations in `src/App.tsx`; domain types in `src/types/index.ts`.

## Current page surfaces

- Batch list on the left: batch ID, status, product, raw kg, lot date.
- Selected batch detail on the right: lot/product/status, raw/allocated/loose figures, allocation table.
- `Create New Batch` wizard: product, batch ID sequence, raw material kg, manufacturing date, dynamic pack allocation rows, allocation kg, MRP, expected pack count and rate per gram, create/cancel.
- `Pack from loose later` modal: pack size, kg to pack, expected packs, confirm allocation.
- Print actions per allocation and for whole batch.

## Confirmed logic defects

1. **Hard-coded starter allocation data.** Initial rows and each new wizard opening contain 100 g / 15 kg / ₹50 and 500 g / 15 kg / ₹220 (`BatchesView.tsx:62–65, 114–127`). They are not sourced from the selected product/SKU. Selecting another product can retain turmeric assumptions. Make allocations start empty or derive only the pack list; never populate unverified price.
2. **Formula-generated MRP.** Additional rows calculate price from ₹50 per 100 g; creation falls back to SKU MRP or a guessed ₹220 / proportional price when missing (`BatchesView.tsx:130–140, 190–214`). The UI copy claims strict compliance but this is not strict. Missing authorized MRP must block batch creation for a required MRP field.
3. **Fallback allocation when no rows.** If all rows are removed, handler adds a default 100 g allocation at ₹50 (`BatchesView.tsx:169–173`). It should reject no allocation or allow explicit save-as-unallocated only if product workflow needs it.
4. **Invalid quantities are silently replaced.** Allocation values `<=0` become 5 kg; `expectedPacks` is forced to at least 1 even when mathematical yield is zero (`BatchesView.tsx:190–194`). Reject invalid values; display zero packs when below one pack and preserve remainder.
5. **Raw material is silently inflated.** `rawMaterialKg: Math.max(rawKgInput, totalAllocKg)` changes entered source quantity to fit allocations (`BatchesView.tsx:218–227`). Block over-allocation instead; never rewrite a human-entered raw amount to hide a discrepancy.
6. **No allocation reconciliation model.** There is no explicit waste, spillage, process loss, quality sample, or yield percentage. Current “loose” is raw minus allocations, not a traceable stock ledger. Add input/output ledger events and require reconciliation before closing.
7. **Pack parser silently defaults.** `parsePackGrams()` returns 100 for empty/invalid input and 1,000 g for malformed numeric kg content (`BatchesView.tsx:87–96`). Parse with a shared strict unit parser. Invalid input should be an error, not 100 g.
8. **Shelf-life date calculation is unsafe at month ends.** `Date.setMonth()` can overflow (e.g., month-end dates), and calculation only uses product `defaultShelfLifeMonths`, ignoring SKU `shelfLifeOverrideMonths` (`BatchesView.tsx:176–188`, type in `types/index.ts:71–73`). Use date-only arithmetic and a documented calendar-month policy; unit-test Feb 29, Jan 31 and all month lengths.
9. **Timezone/date-only mismatch.** UI initializes date using `new Date().toISOString().slice(0,10)`, which is UTC and may not equal the operator's local calendar day near midnight (`BatchesView.tsx:52, 120`). Use local date-only helpers, serialize `YYYY-MM-DD`, and do not let timezone shift a batch date.
10. **Batch ID collision and wrong prefix risk.** IDs are generated by scanning in-memory loaded batches; `maxNum` starts at 13 for every prefix and manual input is accepted without checking uniqueness (`BatchesView.tsx:98–112, 527–533`). Use server-side or single-transaction unique sequence allocation, validate prefix and enforce a unique DB index. Concurrency must be safe.
11. **Generated allocation IDs depend on wall-clock time/index.** `Date.now()` can collide if repeated quickly and allocation ID is not persisted as an independent unique sequence service. Use UUID/ULID; make ID uniqueness a DB constraint.
12. **Fallback SKU IDs are fabricated.** A missing SKU produces `sku_${packSize...}` or `sku_custom` but no matching SKU record (`BatchesView.tsx:200–204, 250–264`). Allocation should reference a real active SKU or a formally created custom pack SKU; foreign-key integrity is essential.
13. **No duplicate allocation validation.** Multiple rows for same SKU are permitted without an explicit reason or merge rule. Merge or warn with clear policy, and make expected-pack totals correct.
14. **Pack sizes can be arbitrary text.** Allowed sizes on a product are not checked; quick dropdown includes 2 kg and 5 kg regardless of SKU. Restrict to active SKUs or require authorized creation of a custom SKU before allocation.
15. **Loose allocation has a fixed best-before date.** `bestBefore='09/11/27'` and MRP fallback ₹50 (`BatchesView.tsx:237–265`) are independent of batch date/SKU rule. Derive expiry from original lot MFD and the applicable shelf-life rule; do not set today's date if material comes from an older lot.
16. **Loose modal permits nonsensical pack size/quantity.** `parseFloat()` can produce NaN or zero; expected pack preview does not validate; a tiny weight can yield 0 packs and still be appended. Block zero pack count or ask whether the remainder stays loose.
17. **Print action loses chosen allocation.** The row sends `(batch, alloc.id)` but the App ignores `allocId` (`BatchesView.tsx:468–472`, `App.tsx:652–655`). Preserve exact allocation in route/state.
18. **Current-batch loose balance can hide negative balance.** `Math.max(0, raw - allocated)` masks over-allocation (`BatchesView.tsx:79–81`). A negative balance should trigger an error/hold.
19. **No lifecycle guard on completed batches.** There are no clear controls to amend or lock completed/archived records, and update callback can overwrite full batch snapshots. Require controlled correction/reversal records, not direct editing of history.
20. **No explicit batch edit/delete/reopen/close workflow.** The imported `Trash2` and other controls do not represent a complete lifecycle. Define role-gated actions with soft archive and audit events.
21. **“Use ↑ ↓ to navigate” is not implemented in the page itself.** Add real keyboard handling and visible focused row or remove the hint.
22. **Clickable batch list uses a `div`.** It is not tab-focusable or keyboard-operable. Use buttons or listbox/option semantics with proper focus state.
23. **Potential stale active batch.** Mutations read batch list snapshots from App and replace whole object; concurrent edits from multiple tabs/users may overwrite each other. Use version/ETag compare-and-swap or transactional field-level operations.
24. **No search/filter/sort.** Batch list will become unusable with time. Add date range, status, product, ID, needs attention, and sort controls; preserve current detail selection.
25. **No visual material-flow breakdown.** Show Raw Input → Allocations → Loose Balance → Documented Loss → Reconciled Yield. Every value must reconcile to the gram or defined precision, with rounding shown.

## Required batch data model changes

Introduce:

- `Batch`: stable id, display batch code, product, lot/manufacturing date, raw input quantity + unit, status, created/updated actor/time, version, notes, archive metadata.
- `BatchAllocation`: ID, actual `skuId`, allocated grams (integer), planned packs, approved MRP snapshot + currency, shelf life rule snapshot, MFD/expiry date-only strings, state and version.
- `MaterialMovement`: append-only event with movement type (`raw_received`, `allocated`, `loose_repacked`, `scrap`, `adjustment`, `return`), quantity in grams, lot, reason, actor, source/destination references, timestamp.
- `BatchReconciliation`: planned vs actual packs, good quantity, reject/scrap quantity, remaining raw/loose grams, discrepancy reason, operator, supervisor approval if threshold exceeded.

Do not store floats as authoritative mass where integer grams or integer mg make more sense. Use `decimal`/integer minor units for money and an explicit rounding policy.

## Batch wizard redesign

Step 1 — Product and lot: product, batch code preview, lot/MFD date, raw quantity/unit. Product's applicable shelf-life rule should be shown.

Step 2 — Pack allocation: searchable SKU selector, allocated mass, MRP snapshot. Show packs = floor(allocated grams / net grams); remainder displayed. Each row has remove, duplicate, and clear actions with accessible labels.

Step 3 — Reconciliation: raw mass, allocated sum, remaining loose, loss. Red block if allocated > raw. Never auto-inflate raw mass. Explain sub-pack leftovers.

Step 4 — Confirmation: all exact fields, date, code, allocations and price sources; warnings and override reasons; Create Batch primary action.

## Batch detail redesign

- Header with status pill + permitted actions: Continue, Create print jobs, Add allocation from loose, Reconcile, Archive.
- Allocation table with row-specific print status, planned vs completed packs, MRP snapshot, date, SKU, template resolution state.
- Each row has **Print this allocation** that passes allocation ID.
- Material ledger panel with event history.
- Timeline: batch created, allocations changed, template/job events, print attempts, reconciliation, close.
- Prevent edits when batch is completed unless Correction / Reopen workflow with audit trail.
